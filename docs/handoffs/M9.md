# M9 — Background consolidation

M9 is the first v0.2 slice. It makes memory consolidation autonomous while
keeping raw interactions and events canonical and append-only.

## Delivered behavior

- An opt-in, in-process worker runs without an HTTP trigger.
- A batch combines interactions and events in chronological order.
- Every candidate memory cites typed interaction and/or event evidence.
- Successful sources cannot be claimed again.
- Failed sources observe a retry delay and maximum automatic-attempt count.
- Manual consolidation bypasses automatic retry limits for controlled recovery.
- Startup marks abandoned `processing` runs as failed with `interrupted`.
- `GET /admin/consolidation/runs?limit=20` exposes bounded operational state to
  principals with `can_consolidate` without exposing source content.
- The existing `POST /admin/consolidate` endpoint remains available.

The worker remains a logically separate module inside Prime. M9 does not add a
queue, scheduler service, Redis, distributed leases, or horizontal-worker
coordination.

## Configuration

| Variable | Default | Purpose |
|---|---:|---|
| `BACKGROUND_CONSOLIDATION_ENABLED` | `false` | Enables the worker after startup validation |
| `CONSOLIDATION_PRINCIPAL_ID` | `system:consolidator` | Active principal recorded on background runs |
| `CONSOLIDATION_POLL_INTERVAL_MS` | `60000` | Delay after one poll finishes before the next starts |
| `CONSOLIDATION_RETRY_DELAY_MS` | `300000` | Cooldown after a failed source attempt |
| `CONSOLIDATION_MAX_ATTEMPTS` | `3` | Maximum automatic failed attempts per source |

The configured principal must already exist, be active, and have
`can_consolidate`. Prime fails startup validation when the worker is enabled
and that contract is not met.

## Production acceptance

1. Apply migration `0006_background_consolidation.sql` and ensure the worker
   principal is active and authorized.
2. Enable background consolidation and restart Prime.
3. Append one novel interaction and emit one novel event. Do not call the
   manual consolidation endpoint.
4. Confirm a `background` run succeeds and claims both source kinds.
5. Retrieve the created memory and verify `evidenceInteractionIds` and
   `evidenceEventIds` identify the canonical records.
6. Wait for another poll and confirm neither duplicate memory nor empty run was
   created.
7. Force one provider failure. Confirm the failed run is visible, no partial
   memory exists, and another poll inside the cooldown does not retry it.
8. Restore the provider and use the manual endpoint to prove controlled retry.
9. Stop Prime during a processing run, restart it, and confirm the abandoned
   run is marked `interrupted` and its sources can be retried.
10. Confirm an unauthorized principal receives `403` from both administrative
    consolidation endpoints.
