# M4 Handoff — Consolidation

## Status

M4 is implemented on `feat/m4-consolidation` and is ready for review.

## Delivered

- `POST /admin/consolidate` runs one explicit, bounded consolidation batch.
- A principal requires the separate `can_consolidate` permission; ordinary
  interaction-ingesting clients receive `403`.
- Source interactions are claimed without changing their canonical rows.
- Active and successful claims prevent accidental duplicate processing.
- Failed claims retain run diagnostics and become eligible for a later retry.
- The consolidation-provider boundary receives bounded interaction batches.
- The OpenRouter implementation requests strict JSON Schema output and then
  validates the returned JSON independently with Zod.
- Every candidate memory must cite one or more interaction IDs from the claimed
  source batch. Foreign or malformed evidence fails the entire run.
- The embedding-provider boundary supports batched embedding generation.
- Memories, embeddings, the actual embedding model, dimensions, generating
  component/model, run, and complete evidence links are persisted atomically.
- A batch that contains no durable memory still succeeds and marks its sources
  processed without calling the embedding provider.
- Provider, embedding, validation, and persistence failures are externally
  visible and recorded without partial memory persistence.

## API contract

Create the trusted principal once:

```bash
pnpm principal:create system:consolidator --can-consolidate
```

Then invoke a batch with that principal's API key:

```http
POST /admin/consolidate
Authorization: Bearer <consolidator-key>
Content-Type: application/json

{}
```

Success:

```json
{
  "status": "succeeded",
  "runId": "019d...",
  "sourceCount": 12,
  "memoryCount": 4
}
```

There is no work when `sourceCount` is zero. A failed external stage returns
HTTP 502; a persistence failure returns HTTP 500. Both return
`error: consolidation_failed` and the recorded run ID. Details remain in
structured server logs and `consolidation_runs`; raw source or memory content is
not written to logs.

## Configuration

Required by the Gremlin Prime runtime:

- `OPENROUTER_API_KEY`
- `CONSOLIDATION_MODEL`
- `EMBEDDING_MODEL`

Optional bounded settings:

- `CONSOLIDATION_BATCH_SIZE` (default `20`, maximum `100`)
- `CONSOLIDATION_MAX_SOURCE_CHARACTERS` (default `200000`)
- `MODEL_REQUEST_TIMEOUT_MS` (default `60000`)

Both provider selectors are fixed to `openrouter` in this slice. The code
depends on provider interfaces, so another concrete provider can be introduced
without changing consolidation orchestration.

The integration suite verifies permission enforcement, memory and vector

and absence of partial memory writes after embedding failure.

## Boundaries and follow-up

- M4 processes interactions only. Event ingestion remains a later v0.1 slice.
- M4 deliberately has no scheduler or background queue.
- M4 has no memory read endpoint, vector index, namespace read policy, semantic
  search, or Chat context injection.
- Derived memories can be discarded and rebuilt from canonical interactions;
  an automated rebuild command is not part of this first consolidation slice.

## M5 entry point

M5 should implement authorized retrieval and Gremlin Chat context injection:

1. Add principal namespace-read policies with hierarchical matching.
2. Embed a bounded search query using the same recorded embedding model.
3. Constrain semantic search by authorized namespaces inside the database query.
4. Expose memory search/get through the Prime application layer.
5. Retrieve a small, configurable memory set in Chat and inject a clearly
   delimited context block before the OpenRouter request.
6. Prove that unauthorized memories never leave Prime.

Do not add MCP or a second client during M5; those remain M6 and M7.
