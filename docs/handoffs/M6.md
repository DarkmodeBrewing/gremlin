# M6 Handoff — MCP

## Status

M6 is implemented on `feat/m6-mcp` and is ready for review.

## Delivered

- Prime exposes a sessionful Streamable HTTP MCP endpoint at `/mcp`.
- Every MCP request authenticates with the existing API-key principal model.
- An MCP session is bound to the principal that initialized it.
- `memory.search` reuses the M5 embedding and database-constrained namespace
  search.
- `memory.get` reuses the M5 authorization-constrained direct retrieval path.
- `memory.timeline` lists authorized memories in reverse chronological order,
  with optional namespace, descendant, time-range, and limit constraints.
- `interaction.append` and the REST interaction route share the same append
  operation and derive source identity from authentication.
- Events are stored as append-only canonical source records.
- `event.emit` and `POST /events` share the same event append operation.
- `GET /events/:id` reveals an event only to its source principal.

## MCP contract

Connect to `POST /mcp` using Streamable HTTP and an existing Gremlin Bearer
credential. Prime exposes exactly these v0.1 tools:

- `memory.search`
- `memory.get`
- `memory.timeline`
- `interaction.append`
- `event.emit`

The MCP transport does not accept a principal identifier as tool input.
Initialization records the authenticated principal and later requests using
that MCP session must authenticate as the same principal.

`memory.timeline` is deliberately a chronological view over derived memories.
It does not dereference evidence interactions because an authorized memory may
have been derived from raw interactions submitted by another principal.

## Event model

Events contain:

- UUIDv7 ID
- occurrence and storage timestamps
- authenticated source principal
- bounded dotted or hyphenated type
- textual content
- validated JSON metadata

Events are append-only. M6 stores them but does not expand consolidation to
process events; that is not needed for the M6 MCP boundary or M7 proof.

Create an interaction-and-event-ingesting MCP principal with:

```bash
pnpm principal:create agent:opencode --can-ingest-events
```

Memory namespace policies remain separately provisioned through
`principal:grant-memory-read`.

## Verification

Run the repository checks:

```bash
pnpm typecheck
pnpm test
pnpm build
```

The PostgreSQL + pgvector suite additionally runs:

```bash
pnpm migrate
pnpm --filter @gremlin/prime test:integration
```

The integration suite verifies tool discovery, MCP session authentication,
ingestion permissions, authenticated source attribution, event persistence,
and namespace filtering across search, direct retrieval, and timeline.

## Production acceptance

1. Deploy the merged revision and apply migration `0005`.
2. Create an MCP client principal with only its required ingestion permissions.
3. Grant only the memory namespaces that client may read.
4. Connect an MCP inspector to `/mcp` using the generated Bearer credential.
5. Verify that all five tools are discoverable.
6. Append one interaction and one event and verify their authenticated source.
7. Verify that memory tools return allowed namespaces and never return a known
   forbidden namespace.

## Boundaries and M7 entry point

- M6 does not connect a second production client or model.
- M6 does not consolidate events.
- M6 does not add scheduling, OAuth, sophisticated RBAC, or memory mutation.
- M7 should connect a second client/model through this MCP endpoint and execute
  the canonical cross-client memory-continuity proof.
