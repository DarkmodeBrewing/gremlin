# M10 — Memory lifecycle and reconstruction

M10 makes derived memory correctable and reconstructible while preserving the
append-only canonical interaction and event archive.

## Delivery plan

### Part 1 — Lifecycle and active-memory filtering

- record terminal lifecycle transitions as append-only audit records
- support deliberate invalidation by an authorized consolidator
- exclude invalidated or superseded memory from search and timeline retrieval
- keep inactive memory available through authorized direct inspection
- expose lifecycle reason, principal, timestamp, and replacement provenance

### Part 2 — Selective reconstruction

- accept explicit interaction and event source references
- permit controlled reprocessing of successfully consolidated sources
- stage replacement memories before superseding prior active memory
- supersede only memories whose complete evidence set was selected
- avoid exact duplicates with the same namespace, content, and evidence set

### Part 3 — Full reconstruction and embedding regeneration

- rebuild derived memory from the canonical corpus into staged state
- leave active retrieval unchanged when a rebuild fails
- activate a completed rebuild safely and retain the previous state for audit
- regenerate embeddings when the configured embedding model changes
- preserve evidence, consolidator, model, version, and run provenance

## Part 1 API

An authenticated principal with `can_consolidate` may invalidate a memory:

```http
POST /admin/memories/:id/invalidate
Content-Type: application/json

{"reason":"Superseded by a corrected canonical observation."}
```

Ordinary memory search and timeline retrieval return active memory only.
Authorized `GET /memory/:id` remains historical inspection and returns the
memory's lifecycle state. Lifecycle transitions never mutate or delete the
canonical evidence records.

## Part 1 acceptance

1. Create two retrievable memories in an authorized namespace.
2. Invalidate one as `system:consolidator` with a non-empty reason.
3. Verify REST `memory.search`, MCP `memory.search`, and MCP
   `memory.timeline` omit the invalidated memory.
4. Verify authorized direct retrieval still returns it with lifecycle details
   and complete interaction/event evidence.
5. Verify a principal without `can_consolidate` receives `403`.
6. Verify a repeated terminal transition returns `409` and does not append a
   second lifecycle record.
7. Verify no interaction, event, evidence, or memory row was deleted.

## Part 1 production acceptance — 2026-09-25

**PASS**, manually verified in production against PR #11 candidate
`5a3aff0de4cb13f78cd8f8f3a2fc2b75bd689d9e` (Brass Badger test).
This records the operator's observed results, not a transcript of credentials
or memory content.

- An active derived memory was visible in ordinary semantic retrieval, with
  namespace authorization enforced.
- A principal without `can_consolidate` received `403` on invalidation.
- `system:consolidator` invalidated the memory with a reason; the transition
  appended one lifecycle event.
- After invalidation, REST `memory.search`, MCP `memory.search`, and MCP
  `memory.timeline` omitted the memory. There is no REST timeline route.
- Authorized direct `GET /memory/:id` still returned the historical memory,
  lifecycle state, reason, actor, timestamp, and supporting evidence.
- A repeat invalidation returned `409 memory_not_active`; exactly one lifecycle
  event existed afterward.
- Database inspection confirmed the memory row, canonical interaction, and
  evidence relationship still existed. This test memory had no event evidence;
  the event evidence count was zero before and after.

Conclusion: canonical history remained immutable while derived knowledge became
correctable. Part 1 is production verified; selective reconstruction remains
Part 2.

## Explicit exclusions from Part 1

- selective reconsolidation execution
- automatic supersession decisions
- full-corpus rebuild orchestration
- embedding regeneration
- semantic duplicate detection
- contradiction or temporal-belief resolution
