# M10 — Memory lifecycle and reconstruction

M10 makes derived memory correctable and reconstructible while preserving the
append-only canonical interaction and event archive.

## Delivery plan

### Part 1 — Lifecycle and active-memory filtering

- record terminal lifecycle transitions as append-only audit records
- support deliberate invalidation by an authorized consolidator
- exclude invalidated or superseded memory from search and timeline retrieval
- keep inactive memory available through authorized direct inspection
- expose lifecycle reason, principal, timestamp, and replacement provenance

### Part 2 — Selective reconstruction

- accept explicit interaction and event source references
- permit controlled reprocessing of successfully consolidated sources
- stage replacement memories before superseding prior active memory
- supersede only memories whose complete evidence set was selected
- avoid exact duplicates with the same namespace, content, and evidence set

### Part 3 — Full reconstruction and embedding regeneration

- rebuild derived memory from the canonical corpus into staged state
- leave active retrieval unchanged when a rebuild fails
- activate a completed rebuild safely and retain the previous state for audit
- regenerate embeddings when the configured embedding model changes
- preserve evidence, consolidator, model, version, and run provenance

## Part 1 API

An authenticated principal with `can_consolidate` may invalidate a memory:

```http
POST /admin/memories/:id/invalidate
Content-Type: application/json

{"reason":"Superseded by a corrected canonical observation."}
```

Ordinary memory search and timeline retrieval return active memory only.
Authorized `GET /memory/:id` remains historical inspection and returns the
memory's lifecycle state. Lifecycle transitions never mutate or delete the
canonical evidence records.

## Part 1 acceptance

1. Create two retrievable memories in an authorized namespace.
2. Invalidate one as `system:consolidator` with a non-empty reason.
3. Verify REST `memory.search`, MCP `memory.search`, and MCP
   `memory.timeline` omit the invalidated memory.
4. Verify authorized direct retrieval still returns it with lifecycle details
   and complete interaction/event evidence.
5. Verify a principal without `can_consolidate` receives `403`.
6. Verify a repeated terminal transition returns `409` and does not append a
   second lifecycle record.
7. Verify no interaction, event, evidence, or memory row was deleted.

## Part 2 API and acceptance

An authenticated principal with `can_consolidate` may request reconstruction of
an explicit, bounded set of canonical sources:

```http
POST /admin/reconstruct
Content-Type: application/json

{"sources":[{"kind":"interaction","id":"<uuid>"},{"kind":"event","id":"<uuid>"}]}
```

The endpoint returns the run ID and counts. Missing, busy, or oversized source
selections return `409 sources_unavailable`; duplicate or malformed references
return `400`. The original `/admin/consolidate` and background worker still
claim only sources without a successful or processing run. Reprocessing does
not rewrite their earlier run records.

1. Derive a memory from an interaction and event, then reconstruct both sources
   with a changed interpretation. Verify the replacement is active and the
   original has one `superseded` lifecycle event referencing the successful run.
2. Reconstruct just the interaction. Verify the memory citing both sources is
   still active because its complete evidence set was not selected.
3. Reconstruct an unchanged interpretation and evidence set. Verify no duplicate
   active memory and no supersession event are created.
4. Fail generation, embedding, or persistence. Verify existing active retrieval
   stays available and the run is marked failed; an empty successful candidate
   set also leaves existing active memory intact.
5. Verify the old memory, all interaction/event evidence links, and canonical
   source rows remain available for historical inspection.
6. Verify `401` without authentication, `403` without `can_consolidate`, and
   rejection of duplicate, missing, or concurrently claimed source references.

Part 2 does not run automatically. Supersession is committed together with the
new derived memories and run status only after generation and embedding succeed.
No semantic equivalence or automatic contradiction decision is inferred.

## Part 3 API and acceptance

An authenticated principal with `can_consolidate` starts an asynchronous full
rebuild with `POST /admin/rebuild` and an empty body. The `202` response gives
`rebuildId`, `runId`, and the count of snapshotted canonical interaction and
event sources. Poll `GET /admin/rebuilds/:id` for `processing`, `succeeded`, or
`failed`, counts, embedding model, and an error code. A second active rebuild
returns `409 rebuild_in_progress`.

The rebuild snapshots source IDs before calling the consolidator. It processes
them in bounded batches and stores new derived memories with their evidence,
generator, model, and run references. Staged memories are excluded from search
and timeline. A failed or interrupted run stays hidden and preserves the old
active state. Successful activation marks the completed rebuild active,
records append-only supersession for previous active memories fully supported
by the snapshot, and switches the search embedding model in one transaction.
Memories citing sources ingested after the snapshot are left active. An empty
result cannot supersede a nonempty active state.

When changing embedding models, configure the new model before starting the
rebuild, but keep the previous model callable through the provider until the
run succeeds: search remains pinned to it while staging. Query embeddings use
the stored active model rather than the provider's new default. The operator
should inspect model availability and provider cost before initiating a full
run; retries start a fresh run and keep failed staged state for audit.

1. Start with an active memory using the old embedding model. Start a rebuild
   using a new configured model, and verify old search/timeline results remain
   available while new memories are staged.
2. Complete the rebuild. Verify new memories and their embeddings appear in
   authorized search, old memories have lifecycle events pointing to the run,
   and direct historical retrieval retains old evidence.
3. Fail a later batch after an earlier one was staged. Verify the run is marked
   failed, staging remains hidden, and old retrieval is unchanged. Restart and
   verify interrupted runs are marked failed.
4. Insert a source after the snapshot and verify an active memory citing it is
   not superseded by activation.
5. Verify authorization (`401`/`403`), concurrent rebuild rejection (`409`),
   and that canonical interactions and events remain intact.

## Explicit exclusions from Part 1

- selective reconsolidation execution
- automatic supersession decisions
- full-corpus rebuild orchestration
- embedding regeneration
- semantic duplicate detection
- contradiction or temporal-belief resolution
