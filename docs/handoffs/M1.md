# M1 Handoff — Infrastructure

Status: Complete  
Implemented in: [PR #1](https://github.com/DarkmodeBrewing/gremlin/pull/1)  
Canonical scope: [Gremlin Prime v0.1 — The Hoarder](../v0.1_spec.md)

## Outcome

M1 establishes a runnable and tested foundation for Gremlin Prime:

- strict TypeScript and pnpm workspace
- Fastify-based Gremlin Prime process
- PostgreSQL 18 with pgvector
- ordered, checksummed SQL migrations
- database-aware `GET /health`
- production container build and Docker Compose stack
- pull-request CI, Compose smoke testing, and CodeQL analysis

## Implementation decisions

- Prime is currently one application. A separate worker process is deferred until background work requires it.
- Database code remains inside Prime. It should become a shared package only when a real second consumer appears.
- Applied migrations are recorded with SHA-256 checksums. Never edit an applied migration; add a new migration instead.
- The migration runner uses a PostgreSQL advisory lock to prevent concurrent migration execution.
- `GET /health` is a readiness check: PostgreSQL failure returns HTTP 503 rather than a misleading successful response.
- Workflow permissions are read-only except for CodeQL's narrowly scoped security-event upload permission.
- GitHub Actions are pinned to full commit SHAs.

## Run and verify

Start the complete stack:

```bash
cp .env.example .env
docker compose up --build
curl --fail http://localhost:3000/health
```

Run repository verification:

```bash
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

CI additionally builds the containers, applies migrations, starts PostgreSQL and Prime, and verifies the live health endpoint. CodeQL scans pull requests, pushes to `main`, and the default branch weekly.

## Known limits

- M1 has no principal authentication or authorization.
- Interactions, events, memories, and provenance are not yet persisted.
- The initial migration only enables pgvector and creates migration bookkeeping at runtime.
- Production secret provisioning, backup, restore, and deployment-host configuration remain operational work outside this milestone.

## M2 entry point

M2 should implement the smallest complete interaction-archive slice:

1. Add principal and interaction schema through a new migration.
2. Authenticate API keys as registered principals; never accept principal identity from request data.
3. Implement `POST /interactions` and `GET /interactions/:id`.
4. Preserve conversation ID, source principal, role, content, timestamps, and sanitized metadata.
5. Test persistence and provenance using real PostgreSQL behavior where database semantics matter.

Before starting M2, read [AGENTS.md](../../AGENTS.md) and the canonical specification. Do not expand into Gremlin Chat, consolidation, embeddings, retrieval, or MCP until their milestones require them.
