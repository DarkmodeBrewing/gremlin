# M5 Handoff — Authorized Retrieval

## Status

M5 is implemented on `feat/m5-memory-retrieval` and is ready for review.

## Delivered

- Principals receive explicit exact or hierarchical namespace-read policies.
- `POST /memory/search` embeds a bounded query with the configured embedding
  provider and searches only memories stored under the provider-returned model.
- Namespace authorization is part of the database query; forbidden memories do
  not enter application-visible results.
- `GET /memory/:id` applies the same authorization and returns HTTP 404 for a
  missing or forbidden memory.
- Direct retrieval includes evidence interaction IDs without exposing raw
  interaction content from another principal.
- Gremlin Chat archives the latest user turn, retrieves a configurable number
  of relevant memories, and injects only those that fit a configurable
  approximate token budget.
- Injected memory is a clearly delimited system context block whose records are
  identified as untrusted JSON data rather than instructions.
- A retrieval failure is visibly streamed after the user interaction is safely
  archived, and OpenRouter is not called with silently empty memory.

## Namespace policy

Grant policies only after migration `0004` is applied:

```bash
pnpm principal:grant-memory-read \
  client:gremlin-chat identity preferences "user/*" "programming/*" "projects/*" "brewing/*"
```

`identity` is exact. `user/*` includes both `user` and descendants such as
`user/pets`. Policies are additive and idempotent. A principal with no matching
policy receives no memories.

## REST contract

Search:

```http
POST /memory/search
Authorization: Bearer <principal-key>
Content-Type: application/json

{"query":"Do you know my cat?","limit":5}
```

Success returns `{"memories":[...]}` ordered by cosine distance. `limit`
defaults to 5 and is bounded to 20. An embedding-provider failure returns HTTP
502 with `memory_search_failed`; a successful search with no authorized match
returns an empty array.

Retrieve one known memory:

```http
GET /memory/<memory-id>
Authorization: Bearer <principal-key>
```

The response includes provenance IDs. Missing and unauthorized IDs both return
HTTP 404.

## Chat configuration

- `MEMORY_SEARCH_LIMIT` defaults to `5` and is bounded to `1..20`.
- `MEMORY_CONTEXT_MAX_TOKENS` defaults to `1200` and is bounded to `100..8000`.

The token budget uses a deliberately simple four-characters-per-token estimate.
It is a context-size guard, not provider billing telemetry.

## Verification

Run the repository checks:

```bash
pnpm typecheck
pnpm test
pnpm build
```

The PostgreSQL + pgvector integration suite additionally runs:

```bash
pnpm migrate
pnpm --filter @gremlin/prime test:integration
```

It proves semantic ordering, hierarchical authorization, direct-retrieval
concealment, provenance, and the distinction between empty results and
embedding failure.

## Production acceptance

1. Deploy the merged revision and apply migration `0004`.
2. Grant `client:gremlin-chat` access to `user/*` (and any other intended
   namespaces).
3. Keep `EMBEDDING_MODEL` on the same stable model used by M4.
4. Start a fresh Gremlin Chat conversation.
5. Ask: `Do you know my cat?`
6. Verify that Gremlin retrieves `user/pets` and answers with `Alvar` without
   receiving the old conversation transcript.

## Boundaries and M6 entry point

- M5 does not add MCP or a second client.
- Exact vector search is sufficient for the v0.1 corpus; no speculative vector
  index or cache was added.
- M6 should expose `memory.search`, `memory.get`, `memory.timeline`,
  `interaction.append`, and `event.emit` through MCP using the same Prime
  application layer and authorization behavior.
