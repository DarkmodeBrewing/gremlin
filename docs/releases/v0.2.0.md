# Gremlin v0.2.0 — Autonomous and maintainable memory

Released 2026-11-15. Annotated tag `v0.2.0` points to
`2a241543b77505764a5959e2601dc21a4cbd4d69`, the accepted main revision including
M10 and the PostgreSQL restart-policy correction.

## Delivered

- M9: background consolidation of interactions and events with explicit retry,
  idempotency and failure state.
- M10.1: append-only memory lifecycle events, active-only ordinary retrieval,
  and authorized historical inspection.
- M10.2: bounded selective reconstruction with evidence-set protection and
  exact-duplicate suppression.
- M10.3: staged full reconstruction and embedding regeneration, transactional
  activation, retained historical evidence and interrupted-run recovery.
- PostgreSQL restart policy persisted as `unless-stopped` in Compose and
  applied to the existing DM01 database container without restarting it.

## Acceptance

[The M10 handoff](../handoffs/M10.md) records the earlier model-migration
acceptance. [The 2026-11-15 report](../reports/M10.3-production-acceptance.md)
records the production rerun: 25 canonical sources, 7 rebuilt memories,
available old retrieval during staging, successful activation and intact
canonical/history evidence. Failure and recovery scenarios were verified in
an isolated PostgreSQL integration environment.

The tested code commit was `9c259f5ed3d6503ff9a5c0182b02cb70f696544c`.
Application code, migrations and lockfile at the release tag match that commit;
intervening changes are documentation and the accepted Compose policy fix.
The release's application verification passed typecheck, build, 38 unit tests
and 39 integration tests. The merged policy fix passed CI and Compose checks.

## Operations and next scope

Preserve existing database volumes and credentials when deploying. A plain
container restart does not reload `.env`; credential renewal requires
recreating the affected application containers with the existing environment.
An explicit stop remains respected by `unless-stopped`.

M11 operations status and the recovery runbook are subsequent work on a
separate feature branch. They are not included in the `v0.2.0` tag. No new
schema migration or data rebuild is required by the restart-policy correction.
