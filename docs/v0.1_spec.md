Gremlin Prime

v0.1 — The Hoarder

Status: Locked initial specification
Date: 2026-08-31
Primary implementation: TypeScript / Node.js
Deployment: Self-hosted / Docker Compose

⸻

1. Purpose

Gremlin Prime is a user-owned persistence and memory layer for AI systems.

Its purpose is to separate long-term history, context and memory from individual:

* AI models
* model providers
* agents
* chat interfaces
* applications

Models are replaceable reasoning engines.

Gremlin Prime owns the persistent information that allows different models and agents to operate with continuity over time.

The fundamental v0.1 hypothesis is:

A conversation can occur through one client and model, be consolidated into long-term memory, and later be recalled by another authorized client using another model.

v0.1 exists to prove this hypothesis.

⸻

2. System Boundaries

Gremlin consists of two separate applications.

Gremlin Prime

The persistent memory infrastructure.

Responsibilities:

* interaction ingestion
* event ingestion
* interaction archival
* memory consolidation
* memory storage
* memory retrieval
* authentication
* authorization
* MCP interface
* REST interface

Gremlin Chat

The first reference client for Gremlin Prime.

Responsibilities:

* conversational UI
* conversation management
* communication with OpenRouter
* interaction ingestion into Gremlin Prime
* retrieval of Gremlin memories
* injection of relevant memory into model context

Gremlin Chat is not the owner of Gremlin’s memory.

It is one client of Gremlin Prime.

Future clients may include:

* Hermes
* OpenCode
* CLI agents
* Brewer’s Toolbox
* other AI applications

⸻

3. Core Principles

3.1 Gremlin owns history

The canonical interaction archive belongs to Gremlin Prime.

Clients contribute interactions to this archive.

No individual client owns the only copy of information required to reconstruct Gremlin’s memory.

⸻

3.2 Raw information is immutable

Raw interactions and events are append-only.

Existing records are not silently modified when circumstances or interpretations change.

Corrections and later observations are additional records.

Administrative deletion for privacy or security is an explicit exceptional operation.

⸻

3.3 Derived memory is disposable

Memories are interpretations of source material.

They may be:

* regenerated
* replaced
* consolidated
* invalidated
* improved

Raw source material remains available for future reprocessing.

A future memory algorithm must therefore be capable of rebuilding Gremlin’s derived memory from historical source data.

⸻

3.4 Models are replaceable

No persistent identity or memory may depend on one particular LLM.

Gremlin should work with:

* OpenRouter models
* local models
* specialized models
* future providers

Changing the model must not destroy continuity.

⸻

3.5 Every client contributes to shared history

Authorized clients may contribute interactions or events.

Examples:

Gremlin Chat ─────┐
Hermes ───────────┤
OpenCode ─────────┼──► Gremlin Prime
CLI ──────────────┤
Future clients ───┘

Information learned through one client can therefore become useful to another.

⸻

3.6 Every client receives only authorized memory

Clients authenticate as principals.

Memory access is enforced by Gremlin Prime.

An AI model never determines its own authorization.

Unauthorized memories must never be returned to the client.

⸻

3.7 Agents do not create authoritative memories

Normal agents contribute source information.

A trusted consolidation process derives long-term memory.

This prevents arbitrary agents from directly asserting permanent facts into Gremlin’s memory.

⸻

4. Three Information Domains

Gremlin distinguishes between:

Interactions

What was said.

Examples:

* user chat messages
* assistant responses
* meaningful agent interactions

⸻

Events

What happened.

Examples:

* Git commit
* brewing gravity measurement
* project creation
* deployment
* purchase
* manually recorded observation

⸻

Memories

What Gremlin has derived as worth remembering.

Examples:

* preferences
* decisions
* project context
* lessons learned
* plans
* relationships
* summaries
* persistent facts

Conceptually:

INTERACTIONS ──┐
               │
               ├──► CONSOLIDATION ──► MEMORIES
               │
EVENTS ─────────┘

Interactions and events are source material.

Memories are derived information.

9. Memory Model

A memory is derived information produced from interactions and/or events.

Conceptual fields:

Memory
id
namespace
content
confidence
embedding
embedding_model
generated_by
generated_at
evidence
metadata

namespace

Logical authorization/category boundary.

Examples:

identity
preferences
programming
projects/gremlin-prime
brewing
infrastructure
personal
finance

Namespaces should support hierarchical matching.

content

Human-readable representation of the derived memory.

confidence

Confidence assigned by the consolidation process.

v0.1 does not require sophisticated probabilistic reasoning.

evidence

References to source interactions/events supporting the memory.

generated_by

Identifies the consolidator/model/version responsible for creating the memory.

This is essential for future regeneration.

10. Provenance

Every derived memory must retain provenance.

Example:

Memory
  │
  ├── "Gremlin Prime uses immutable raw interactions."
  │
  ├── confidence: 0.98
  │
  ├── generated_by: consolidator-v1
  │
  └── evidence
        ├── interaction:abc
        ├── interaction:def
        └── interaction:ghi

Gremlin must be able to determine why a memory exists.

⸻

11. Consolidation

v0.1 includes a minimal working memory consolidator.

Its responsibility is to transform source information into candidate long-term memories.

Initial flow:

unprocessed interactions/events
              │
              ▼
        Consolidator
              │
              ▼
         LLM extraction
              │
              ▼
      structured memories
              │
              ▼
       embedding generation
              │
              ▼
         memory store

The consolidator may use:

* inexpensive OpenRouter models
* local models
* another configurable provider

The consolidation provider must be abstracted.

⸻

12. Consolidation Trigger

v0.1 must support explicit/manual consolidation.

Example:

POST /admin/consolidate

Automatic scheduled consolidation is optional for v0.1.

This deliberately avoids requiring a scheduling subsystem to prove the architecture.

The design must permit scheduled/background consolidation later.

⸻

13. Reprocessing

Source records must track whether and how they have been processed without modifying their original semantic content.

Gremlin must eventually support:

interaction history
       │
       ▼
delete/invalidate derived memories
       │
       ▼
new consolidator
       │
       ▼
rebuild memory

A complete automated rebuild command is desirable but not required for the first vertical slice.

The data model must make it possible.

⸻

16. Authentication

Every external client connecting to Gremlin Prime authenticates as a principal.

v0.1 uses API keys.

Example:

API key
   │
   ▼
principal
   │
   ▼
authorization policy

Example principals:

client:gremlin-chat
agent:hermes
agent:opencode
system:consolidator

API keys must be stored securely and must never appear in interactions, events or memories.

Rate limiting is a Gremlin Prime API invariant.

Every externally reachable API endpoint except operational health checks must be rate-limited before credential lookup, database access or other expensive application work. This boundary is enforced inside Gremlin Prime; an ingress proxy may add stricter limits but must not be the only enforcement point.

Exact thresholds and limiter storage are deployment decisions. A shared limiter store is required before Gremlin Prime runs with multiple replicas.

⸻

17. Authorization

Authorization is enforced inside Gremlin Prime.

Clients cannot self-declare their permissions.

v0.1 requires:

* authenticated principals
* namespace-based memory read permissions
* interaction/event ingestion permissions
* trusted memory-write permission for the consolidator

Example conceptual policy:

client:gremlin-chat:
  read:
    - identity
    - preferences
    - programming/*
    - projects/*
    - brewing/*
  ingest:
    - interactions
agent:opencode:
  read:
    - programming/*
    - projects/*
    - infrastructure/*
  ingest:
    - interactions
system:consolidator:
  read_source: true
  write_memory: true

The exact configuration representation is an implementation decision.

Sophisticated RBAC is explicitly outside v0.1.

⸻

18. Authorization Invariant

Memory filtering happens before results leave Gremlin Prime.

Conceptually:

memory.search
      │
      ▼
authenticate principal
      │
      ▼
resolve allowed namespaces
      │
      ▼
perform constrained search
      │
      ▼
authorized results only

An unauthorized memory must not be retrieved and subsequently filtered by the client or model.

20. MCP Interface

v0.1 exposes memory retrieval through MCP.

Required tools:

memory.search
memory.get
memory.timeline

Ingestion should also be available through MCP where practical:

interaction.append
event.emit

MCP uses the same application/service layer as REST.

Authorization behavior must therefore be identical regardless of transport.

Gremlin Chat is the reference implementation proving integration.

It requires:

* basic conversation UI
* conversation/session management
* backend API
* configurable OpenRouter model
* streaming responses if practical
* Gremlin interaction ingestion
* Gremlin memory retrieval
* memory context injection

It does not require:

* polished UX
* attachments
* image generation
* voice
* multi-user support
* elaborate conversation organization

23. Memory Context Injection

Gremlin Chat automatically retrieves a limited amount of relevant memory before an LLM request.

The initial algorithm may simply perform semantic search using the user’s latest message.

Example:

User message
     │
     ▼
memory.search
     │
     ▼
top N authorized memories
     │
     ▼
context block
     │
     ▼
OpenRouter request

Token budgeting must be configurable.

Advanced retrieval strategies are outside v0.1.

24. Data Export

Raw source data is the irreplaceable asset.

v0.1 must provide or make trivial an export of:

* interactions
* events

Preferred format:

JSONL

Derived memories may also be exported but are not canonical.

The source export must contain sufficient information to reconstruct historical source records independently of Gremlin Prime.

29. v0.1 Acceptance Test

The definitive acceptance test is:

Step 1

Start Gremlin Prime, PostgreSQL and Gremlin Chat.

Step 2

Using Client A / Model A, have a conversation containing information Gremlin has never previously observed.

Example:

"We've decided Project Foo will use technology Bar because of reason Baz."

Step 3

Verify the raw conversation has been archived.

Step 4

Run consolidation.

Step 5

Verify one or more derived memories exist with provenance linking them to the original interaction.

Step 6

Start Client B / Model B.

Client B must not receive Client A’s complete conversation history.

Step 7

Ask Client B a question requiring information from the previous conversation.

Step 8

Client B retrieves the relevant memory through Gremlin Prime.

Step 9

Client B answers correctly using that memory.

Success means:

Client A
Model A
   │
   ▼
Interaction
   │
   ▼
Gremlin Prime
   │
   ▼
Consolidation
   │
   ▼
Persistent Memory
   │
   ▼
Client B
Model B

If this works, the central architecture has been proven.

30. Definition of Done

Gremlin Prime v0.1 is complete when:

* raw conversations are persistently archived
* multiple principals can ingest interactions
* interactions retain source provenance
* events can be ingested
* consolidation produces derived memories
* memories retain evidence links
* memories receive embeddings
* authorized semantic retrieval works
* unauthorized namespaces are excluded server-side
* Gremlin Chat consumes memory
* MCP exposes memory to another client
* raw history can be exported
* the cross-client acceptance test succeeds

No additional feature is required for v0.1.

⸻

31. Architectural Invariants

The following are considered locked design principles for v0.1.

I. The model does not own memory.

II. The client does not own memory.

III. Gremlin Prime owns the canonical historical corpus.

IV. Raw source material is preserved independently of derived memory.

V. Derived memory can be rebuilt.

VI. Every source is attributable to a principal.

VII. Every agent contributes to shared history.

VIII. Every agent receives only authorized memory.

IX. Authorization is enforced by Gremlin Prime, never by the model.

X. Normal agents cannot directly create authoritative long-term memories.

⸻

32. North Star

Gremlin Prime should eventually make this possible:

Start a conversation with an entirely new model, through an entirely new interface, on an entirely new machine — and continue where you left off.

The interfaces will change.

The agents will change.

The models will change.

The providers will change.

The history and memory remain yours.
